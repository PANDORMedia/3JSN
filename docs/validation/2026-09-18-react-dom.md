# Upstream React DOM on the native UI tree

Recorded on 2026-09-18, macOS arm64, native Metal and Chrome 153. This is a
bounded compatibility checkpoint for an original public fixture. It does not
adopt a custom React renderer or certify arbitrary React applications.

## Result

The unchanged [fixture](../../fixtures/react-dom/README.md) uses upstream React
19.3.0 and React DOM 19.3.0 to construct its dashboard under an empty container.
Three.js 0.186.0 renders the adjacent canvas. Both parser variants completed the
same React verification and **120 native Metal presentations** after the real
build CLI bundled and relocated them. No HTML payload, network access or access
to the source checkout's development files was needed by these native runs.

The [final React report](2026-09-18-react-dom/react-report.json) records matching
React observations across Chrome, native CPU execution and native windows:

- Asynchronous initial rendering and passive effects, without `flushSync`.
- State, class, inline CSS, custom properties and mixed text/element updates.
- Delegated bubbling clicks, target/currentTarget identity and cancellation.
- Keyed insertion, reordering and removal with surviving node identity.
- Effect cleanup, root unmount and remount with fresh nodes and reset state.

The independent generic DOM checks include Text coercion and identity, live
collection reflection, safe insertion errors, document-root replacement,
attribute reflection and CSS declaration updates. One observation differs:
for an earlier element with `name="shared"` and a later element with
`id="shared"`, native `HTMLCollection` lookup returns the earlier element while
the tested Chrome returns the ID match. Native follows the
[DOM first-match rule](https://dom.spec.whatwg.org/#dom-htmlcollection-nameditem).
The four `knownDifferences` entries retain this one difference in each parser
mode's CPU and window results. `reactObservationsEquivalent` and
`otherTestedDomObservationsEquivalent` are true;
`testedSemanticObservationsEquivalent` is deliberately **false**.

## Implementation boundary

The native bindings expose ordinary DOM operations to upstream React DOM. They
mutate the existing authoritative Blitz document through shared Rust operations;
there is no React-specific visual tree, layout engine, framework patch or
substitute React implementation. The current generic additions cover Text and
Comment wrappers, live child collections, node identity and relationships,
`insertBefore`, attribute removal, inline CSS reflection and validation before
tree mutation. Detached wrappers retain their nodes until realm teardown.

A small pinned Blitz CSSOM patch fixes exact-empty-value removal and declaration
updates through Stylo's public update API. Whitespace-only ordinary CSS values
remain invalid instead of deleting a property; custom-property whitespace is
retained according to the observed serialization. Setting a value can update its
importance and preserve unrelated declarations. Six dependency-level tests and
the shared browser/native fixture cover those cases. This is an inline-style
repair, not a general CSSOM certification; the separate stylesheet-rule setter
and initial mixed-priority declaration ordering are outside these checks.

React reconciliation, JavaScript effects, style evaluation, layout and text
shaping still involve CPU work. GPU composition uses the existing native canvas
bridge: the receipts establish native device/queue identity and report
`cpuImageTransport:false`. They do not measure a speedup or prove that every
operation involved in displaying HTML executes on the GPU.

## Failure investigation and frame completion

An earlier run of the expanded contract failed after successful React
verification with a WebGPU `colorAttachments` sequence conversion error. Its
[failure report](2026-09-18-react-dom/react-failure-report.json) and
[raw logs](2026-09-18-react-dom/react-failure-logs.json) are retained. An unchanged
isolated rerun completed, so that rerun alone was not treated as a repair.

Source inspection found a completion race: the worker could send the final
presentation event and begin another callback while the main thread responded
by terminating V8. A failed V8 call inside WebIDL conversion can become the
observed sequence TypeError. Diagnostic instrumentation also observed an error
after 120 presentations with close requested, which the old message-based
termination filter suppressed. This supports the race explanation; the original
conversion failure did not include enough instrumentation to prove its exact
timing independently.

The frame limit now belongs to the rendering worker, which exits immediately
after the final successful presentation, before further input or animation
callbacks. The main thread waits for worker completion without interrupting V8
on that successful path. Forced interruption for close requests and deadlines
remains separate; no blanket application-error suppression was added.

The focused [completion report](2026-09-18-react-dom/completion-report.json)
passes 12 positive runs: limits 1, 4 and 120, repeated twice in each mode, with
exact callback counts and no work after the final presentation. Four deliberate
JavaScript/invalid-WebGPU-descriptor failures still exit 1 without a success
receipt. The [diagnostic report](2026-09-18-react-dom/shutdown-diagnostic-report.json)
also retains an input-queue overflow encountered before this repair. This
checkpoint does not claim to fix input flooding, arbitrary forced cancellation
or all lifecycle races.

## Reproduction and executable identities

After preparing the pinned native dependencies, build the experimental runtime
with default features and with `--no-default-features`, copying each executable
before the next build. See the
[runtime instructions](../../experiments/compiled-ui-runtime/README.md). Then run:

```sh
node scripts/probe-react-dom.mjs \
  --preserved /path/to/preserved-runtime \
  --restricted /path/to/restricted-runtime \
  --font /path/to/DejaVuSans.woff2 \
  --browser '/Applications/Google Chrome.app/Contents/MacOS/Google Chrome' \
  --out artifacts/react-dom-new-run

node scripts/probe-dom-window-completion.mjs \
  --preserved /path/to/preserved-runtime \
  --restricted /path/to/restricted-runtime \
  --font /path/to/DejaVuSans.woff2 \
  --out artifacts/dom-window-completion-new-run
```

The React harness uses development React consistently in Chrome, CPU and window
checks, matching the unmodified CLI's bundling default. It verifies the original
and disposable copied source, relocates to paths containing spaces, Unicode and
`#`, removes the copied input, and denies network and development-file reads.
Negative `cat` controls establish that the read-denial policy is active.
`--cpu-only` intentionally omits native-window evidence.

## Validation and evidence

- Twelve shared Rust DOM/parser-guard tests and six pinned inline-CSS tests pass.
- Nine runtime package-option tests pass in each parser mode. Both runtime modes
  pass Clippy on the binary and package-option test targets. Formatting passes.
- Workspace tests pass: 33 passed, two existing ignored GPU tests. Workspace
  Clippy passes. Node tests pass: 143 passed, one existing skipped test.
- The final [parser regression](2026-09-18-react-dom/parser-report.json) passes
  its browser/CPU comparison, restricted-operation controls and 120 Metal frames
  per mode with these same executables.
- The final [font-package regression](2026-09-18-react-dom/fonts-report.json)
  passes all 43 steps: 28 declared faces backed by 25 packaged font files,
  byte-identical offline rebuilds, 14 negative controls per mode, relocated
  native verification and 120 Metal frames per mode.
- Dependency preparation checks pass for the normal, positioned and baseline
  generated workspaces. The latter two were not rebuilt for this checkpoint.

The evidence directory contains compact full reports, raw process logs,
manifests, build metadata, sandbox policies, check receipts and source/archive
identities. No runtime binaries, dependency sources, font bytes or acceptance-game
assets are committed there. CI checks the repository's configured scope; it is
not a replacement for the local Metal-window evidence.

A separate visual inspection launched the same preserved executable and payload
in a local macOS app wrapper. The dashboard, text, controls and animated torus
knot were visible. An OS click on **Advance task** visibly changed the count from
0 to 1, the phase to advanced, and the panel styling. This is one observed native
click, not comprehensive input testing or browser/native pixel equivalence. The
dashboard currently exposes no semantic accessibility controls through the
native window's accessibility tree.
